⚡TL;DR — direct answers to the four questions

This is the compressed version of everything below. The design has been updated to reflect the final decision: the bot forwards into one private group, not to individual chat IDs.

❶ How can my whole team see OTPs, instead of only the person sitting in front of the app?
Today the app is a single-machine desktop program — one screen, one operator, no network layer at all (no server, no database). The cleanest and fastest fix is a Telegram bot that pushes into one private group: an OTP lands on any SIM, and within seconds every team member's phone buzzes. Note — your own project roadmap (Memory/05-feature-roadmap.md) already lists "Telegram Bot & Webhook SMS Forwarding" as Feature #1, high priority. Your instinct matches the plan.
❷ Can anyone on Telegram use the bot? Or only my team?
With the group design, the answer is beautifully simple: the group is the allowlist. Anyone who somehow finds the bot's username can press Start and even message it — the bot stays completely silent in private chats and has exactly one configured destination: your group's chat ID. A stranger can't get anything unless an admin invites them into the group. Membership is granted and revoked with Telegram's own group admin tools — the app never manages per-person IDs.
❸ How does it connect locally, and how does it work?
Nothing changes on the hardware side: SIM Bank → USB → the PC running this app, exactly as today. What gets added is one Forwarder module inside the app that makes an outbound HTTPS (port 443) call to api.telegram.org every time a new SMS arrives. Requirements: the PC has internet, the app is running with Live mode ON (an "Auto-start Live Mode" setting already exists), and the bot is a member of your private group.
❹ Will it actually be able to read the SMS OTPs?
It already does. This app ships a full OTP extraction engine (extract_otp): 4–8 digit codes, keyword-gated cascade patterns, and even Myanmar numerals (၀၁၂၃…). The bot simply forwards what the app has already decoded — the hard part of the pipeline is finished. Only the "way out" is missing.

1First — GSM hardware in plain words

Before designing the bot, it helps to actually understand the machine underneath. It's simpler than it looks.

📡 What is a GSM modem?

A GSM modem is the working guts of a phone, without the screen and keyboard — a SIM slot, a radio, and a serial interface. You don't tap on it; your computer talks to it with text commands called AT commands.

A SIM Bank (GSM modem pool) packs 8 / 16 / 32 / 64 of those modems into one chassis with an internal USB hub and a single USB cable out. Plug it into a PC and the OS sees that many serial ports — /dev/ttyUSB0…31 on Linux, COM3…COM34 on Windows. One port = one SIM.

⌨️ AT commands — the language the modems speak

Plain text commands, industry-standard since the 90s. This app uses exactly these:

CommandMeaningTypical reply
AT"Are you alive?" — liveness probeOK
AT+CCIDRead the SIM's ICCID (card identity)8968...15 digits
AT+CMGF=0Switch to PDU mode — SMS as binary dataOK
AT+CMGL=4List every SMS stored on the SIMlong PDU dump
+CMTI: "SM",5Unsolicited: "a new SMS just arrived, stored in slot 5"(what Live mode listens for)
AT+CMGD=5Delete the message in slot 5OK

📦 SIM storage is tiny

A SIM card holds only 20–50 messages. When it's full, the modem silently rejects new SMS. That's why this app already includes a periodic SIM sweep (every 10 minutes) — it keeps slots free.

🧩 PDU mode & Myanmar text

SMS arrives as a hex blob (PDU). This app decodes GSM-7 (English), UCS-2 (Unicode — including Myanmar script), and stitches multi-part concatenated messages back into one.

2How the current project works — and where it stops

One sentence summary: a superb engine with no exhaust pipe. Everything ends at one person's eyeballs.

What's missing today

  • No network layer at all — the app doesn't use the internet (except update checks)
  • Messages live in RAM — closing the app wipes history
  • Visibility = whoever is physically at the screen

What's already perfectly ready

  • Live mode — the +CMTI watcher that catches new SMS instantly ✅
  • OTP extractor — extract_otp, Myanmar digits included ✅
  • The sms:new event — an internal "new message!" signal already firing in exactly the right place ✅ — the perfect hook point for a forwarder
💡 Key insight: the hardest parts of an OTP-bot (reading SMS, decoding, extracting the code) are already done in this project. What's missing is the last mile — a door to the outside.

3The bot design — push into a private group

The destination of every OTP is one private Telegram group. Whoever is a member of the group gets everything; whoever is removed sees nothing more. Membership is the permission system.

🤖 Telegram bots — the 30-second model

  • A bot is a special user account created via @BotFather. You get a token (looks like 123456:ABC-...) — that token is the bot's identity and password at the same time.
  • The bot doesn't run on Telegram's servers — your app calls Telegram's API over the internet using the token. That's why this design needs no port forwarding, no public IP, no server of your own.
  • Bots cannot start conversations — Telegram blocks that. A user must open the bot once and press Start… but with the group design this doesn't matter: the bot is a group member, so it's allowed to speak there (with a small rate limit — see §3.2).
  • Bots in groups normally only see commands unless "Group Privacy" is off — irrelevant here too: we don't listen for anything, we only send.
⚠️ Push-only design: the bot never listens, never replies, has no commands. It receives nothing from anyone — it only ships OTPs out. Attack surface: minimum.

3.2 — Rate limits (why the queue matters)

Telegram's limits

  • ~20 messages/minute into a group — the practical constraint
  • ~30 messages/second globally per bot
  • Exceed it and Telegram replies 429 Too Many Requests with a retry_after field — you just wait that many seconds and resend

The design's answer

  • A paced queue: one send every ~3 seconds, 20/min worst case — under the limit
  • Honors 429 retry_after if a burst ever slips past
  • OTPs expire in minutes; a 3-second pacing is invisible

4Access control — the group IS the allowlist

One configured destination, zero per-person management. Telegram's own group admin tools become your permission system.

Onboarding — 5 steps, once

⚠️ The supergroup gotcha: if a basic group is upgraded to a supergroup (this happens automatically when you enable certain features like group auto-delete or admin-only posting), its chat_id changes to a new -100… value. Symptom: forwarding silently stops. Fix: press Detect Group ID again. Better fix: make the group a supergroup from day one, so the ID never changes under you.

✅ Advantages of this model

  • Zero user management in the app — add/remove people with Telegram's own tools
  • Members don't need to /start the bot or share any ID with you
  • New employee onboarded in one group invite
  • Audit trail for free — Telegram's own chat history is the log
  • The bot token can only ever write to that one group

Trade-offs to accept

  • All members see all OTPs — including sensitive accounts. That's the design: speed over compartmentalization
  • Message history lives on Telegram's servers (mitigate: enable the group's auto-delete timer)
  • Anyone who gets into the group gets everything — protect group invites like passwords

5Network & "local" — what runs where

A common point of confusion: the SIM bank is local hardware, but Telegram is a global service. The app is the bridge.

ThingWhere it livesWhat reaches the internet?
SIM bank + SIMs 🏠 next to your PCOnly one outbound connection:
api.telegram.org:443 (HTTPS)
Nothing listens. Nothing accepts inbound.
The app (Rust + Svelte) 🖥️ that same PC
OTP messages 🧠 RAM (2-hour window)
Telegram servers ☁️ Telegram (global)— they receive the message and fan it out to your group

🏠 LAN-only alternative (rejected)

One could run a tiny local web server and let phones on the same Wi-Fi poll it. Rejected because:

  • No push — phones must poll or keep a page open
  • Breaks the moment the phone leaves your Wi-Fi
  • Port/IP management is its own little hell

☁️ Telegram approach (chosen)

The PC makes an outbound HTTPS call; Telegram's infrastructure does the fan-out:

  • True push — works on any network, anywhere on Earth
  • No port forwarding, no static IP, no DNS
  • Delivery + notification handling is Telegram's problem, not yours
🇲🇲 Myanmar reality check: api.telegram.org has been fully blocked by some ISPs during internet shutdowns. The Forwarder will log a clear error if it can't connect. The planned fix is a SOCKS5 proxy setting (one field in Settings) — Bot API traffic works fine through socks5h:// proxies. MTProto proxy links only help Telegram's client apps, not bot API calls.

7Roadmap advice — build order

The order below is chosen so that every phase is useful on its own, and nothing is thrown away later.

PhaseWhatEffortWhy this order
0 Group-based forwarder — MVP (this doc) small Maximum value for minimum code: one HTTP call at the sms:new hook. Nothing else changes.
1 Hardening: 429 handling, offline retry queue, token masking in logs small Makes the MVP survive real networks (and honor AGENTS.md's no-secrets-in-logs rule).
2 Persistent message history (SQLite) + search medium RAM-only history is the app's biggest existing weakness — and it pairs with the Telegram audit trail.
3 Multi-destination: N groups, per-SIM routing rules ("KBZPay SIM → finance group") medium Once one destination works, N is a table — but only after the single-group flow has proven itself.
4 HTTP API / web dashboard for integration into your own systems large The heaviest option — worth it only if other software must consume OTPs programmatically.
💡 Honest recommendation: ship Phase 0 exactly as described here and live with it for two weeks. The pacing, the bubble format, the masking — all of it is cheap to change after real usage. Don't design phase 3 before phase 0 has run in production.

8FAQ

Does every team member need to open the bot and press Start?
No. That rule only applies to bots messaging users privately. Because the bot speaks inside your group, group membership alone is enough. Members never interact with the bot directly at all.
What if someone finds the bot and messages it?
Nothing. The bot is push-only: it never polls for updates and has no command handlers. A stranger pressing Start sees silence — the bot's only configured destination is your group's chat_id.
Can someone fake the bot and inject a fake OTP?
Not via Telegram's normal surface — posting as the bot requires the token, which lives only on your PC. Protect the PC, protect the token. If a token ever leaks, @BotFather's /revoke kills it instantly and issues a new one.
How do I remove someone's access?
Remove them from the group — that's it. In Telegram, instantly. No app setting touches people.
What happens if the PC has no internet?
OTP delivery pauses; SMS keep accumulating on the SIMs and in the app. With the Phase-1 retry queue, pending messages ship out when connectivity returns. The 10-minute SIM sweep keeps slots from filling meanwhile.
Do all OTPs go to everyone?
Yes — in the single-group design, everyone in the group sees every OTP. It's simple and fast. If you later need "finance OTPs only for the finance team", that's Phase 3's per-SIM routing — built on the same foundation, nothing redone.
Why a group at all, instead of DMing each person?
Three reasons: (1) no per-person chat_id bookkeeping — membership is managed where your team already lives, in Telegram; (2) one send per OTP instead of N sends (gentler on rate limits); (3) shared visibility — anyone can grab a code without asking "did anyone see the KBZPay OTP?".
Is Telegram safe for OTPs?
Reasonable: TLS in transit, no default E2E for group chats, history on Telegram servers. Mitigations built into this design: private (invite-only) group, auto-delete timer, optional code masking (••••••), and instant revocation. For most teams the convenience outweighs the residual risk — but that's your call to make consciously.
Does this work with Myanmar-language OTPs?
Yes — the decoder already handles UCS-2 Myanmar text, and extract_otp recognizes Myanmar numerals (၀၁၂၃…). The forwarded bubble keeps the original message body.
How fast is delivery, really?
~3–8 seconds from SMS arrival to buzz on the phone: the app already decodes in well under a second, the forwarder formats instantly, and the queue only adds ~3 s under heavy bursts. Normal case: you hear the phone before you finish switching windows.
